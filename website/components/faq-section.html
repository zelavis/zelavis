Frequently asked questions

Everything you need to know about self-hosting, architecture, and technology choices.

What does Zelavis replace?

Zelavis combines the platform capabilities engineering teams usually stitch together from separate tools: backend-as-a-service (auth, database, real-time), CMS (schemas, entries, media), hosting control panels (domains, deployments, logs), and functions/workloads platforms. You can run the entire platform unified or embed specific subpaths.

Can I run it completely on my own infrastructure?

Yes. Self-hosting is a foundational architectural requirement, not an afterthought or enterprise-only export. Zelavis is designed to host applications directly on your own VPS, bare-metal servers, or private cloud, with managed Zelavis Cloud offered as a seamless option.

Is Zelavis tied strictly to SQLite?

No. The database storage engine operates over an ordered key-value boundary. While SQLite is the zero-config default, RocksDB and LMDB drivers are built in and operate behind the identical logical database API and multi-model projections.

Does a single-node setup still use the sharded architecture?

Yes. Every official Zelavis App is physically and locally sharded from the moment of creation. On a single server, the virtual shard ranges simply colocate on one machine. When you scale horizontally, the platform moves shard placements rather than forcing an architectural rewrite.

Which parts are implemented and usable today?

The core runtime, Node process isolation, multi-model document/column/measure/graph projections, authentication foundations, background workloads, official @zelavis/ui dashboard, and native server hosting are implemented. Real-time multiplayer collaboration and team issue planning are committed roadmap milestones.
