Architectural Decision Matrix

Zelavis intentionally does not force a single database engine onto every deployment. Storage is an ordered key-value abstraction (KvEngine) that routes tenant data through a partition map into virtual shard ranges. Here is when and why to select each engine:

node-sqlite (Default Engine) Built into Node

Requires no external compiler, C++ toolchains, or native downloads. Highly optimized WAL mode delivers ~5,600 unbatched writes/second. Ideal for standard web applications, edge nodes, and local development.

  • ✔ Zero dependencies & bulletproof portability
  • ✔ Physically sharded out of the box with Fabric
  • ✔ Completely bounded in-process buffer pool
  • ✖ Slower than RocksDB when data vastly exceeds RAM
rocksdb-js (High-Scale Production) Massive Datasets

LSM-tree engine designed by Meta for datasets 10× larger than RAM. Block compression shrinks disk footprint by up to 7.7×, making network replication and shard transfers significantly faster.

  • ✔ 4.5× to 7.7× smaller disk footprint
  • ✔ Immune to cold-cache SSD page-fault cliffs
  • ✔ Sequential append-friendly storage wear
  • ✖ Needs prebuilt binary module (@harperfast/rocksdb-js)
LMDB (In-Memory Microsecond Cache) Zero-Copy Reads

Memory-mapped B+tree delivering sub-microsecond point reads and scans. Shared across multiple Node.js worker processes on a host without IPC overhead.

  • ✔ Blazing-fast in-memory read throughput (22k+ obj/s)
  • ✔ Instant cache warmth across host restarts
  • ✖ High disk footprint & slow unbatched writes (200 tx/s)
  • ✖ Can trigger container cgroup OOM when cold
libSQL (Turso Cloud Bridge) Cloud Primary Sync

SQLite fork built for edge-to-cloud synchronization. Used in Zelavis for connecting to remote Turso database clusters and replicating primary data to edge nodes.

  • ✔ Native compatibility with Turso cloud infrastructure
  • ✔ Remote primary sync protocol support
  • ✖ Highest disk file size among all local engines
  • ✖ Slower than local node-sqlite for pure standalone storage
